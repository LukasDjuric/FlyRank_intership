Which pages should an editor review first? Ranking CTR opportunities in search data

Luka Đurić, FlyRank ML Internship 2026 (Applied Search Intelligence track)

November 2026. Code and notebooks: GitHub repository

Abstract

Out of roughly 91,000 web pages that earn search impressions, which ones should an editor look at first because they get fewer clicks than they should? I used FlyRank’s pseudonymized warehouse release (daily Google Search Console data, March to June 2026, 37 clients), built every feature from March to May only, and graded rankings on two June outcomes, comparing a hand-written rule against logistic regression, a shallow decision tree and a random forest on five folds that hold out whole clients. For the outcome “the page’s CTR stays below what its position normally earns”, the forest placed 0.97 correct pages in its top 50 against 0.76 for the rule (base rate 0.57) and was ahead in all five folds, although part of that skill is persistence of a gap the features already show. For the outcome “the page loses at least 20% of its impressions”, the forest’s 0.85 against 0.76 (base rate 0.70) is directional only: it is ahead in three of five folds and the interval includes zero. I turned the results into a six-action playbook with human-review rules and a client cap, so the queue is a CTR and metadata review list and not a decline detector. This is decision-support evidence from one month; it does not show that editing a page improves it.

Scope. The project started as “CTR and engagement” scoring. Engagement data (GA4) covers only 4.2% of the March rows, so engagement was not tested and this paper is about CTR. Decline is reported as a second, weaker outcome.

1. Introduction

FlyRank publishes content straight into client websites and then watches search data. Content that ranks in Google tends to decay: positions slip, clicks drop, and the team notices late. The valuable decision is small and practical. Out of thousands of pages, which one should a person fix first, given a few hours a week?

Today the product answers with hand-written rules: thresholds for staleness, volume or CTR. They run in production and they are easy to read. The question for this project is whether a learned ranking, trained on observable search signals and checked honestly, ranks pages better than a transparent rule, and where it does not.

Who acts and what it costs. An editor or SEO analyst reads the ranked list from the top and decides whether to check a title and snippet, check for a technical problem, or leave the page alone. A wrong pick costs review time (about 12 minutes per page is assumed here) and, if someone skips the check, possibly a bad edit. For that reason the output is a list for people, not an automatic action.

CTR (click-through rate)
Clicks divided by impressions. Here it is a percentage, so 0.32 means 0.32%.
Position tier
A page’s average rank in search results, bucketed: top 3, page 1, striking (11–20), pages 3–5, deep. CTR falls with position, so CTR is only compared inside a tier.
Precision@K (P@K)
Of the K pages a ranking puts first, the share that really had the problem. K = 50 means a reviewer with time for 50 pages.
Base rate
The share of all pages that have the problem. Picking pages at random gives a P@K equal to the base rate, so every score is read next to it.
Client-grouped validation
Training on some clients and testing on clients the model never saw, because pages of one client share habits a model can memorize.
Leakage
Information that would not exist at prediction time slipping into the features, which makes scores look better than they are.
Persistence
A page that under-captures clicks for three months tends to keep doing so in the fourth. A model can score well by learning only that.

What I left out, and why.

  • Raw queries, URLs, titles, keywords and client names: not in the release, and never shown here.
  • Product decision flags (health score, “needs CTR fix” and similar): not in the release. If rebuilt, they would be baselines, never features.
  • Client and content identifiers: used only for joins and for grouping folds, never as features.

  • The 90-day query table: its window overlaps June, so its totals would contain the outcome.
  • 49 pages (0.1%) with an average position below 1, which is not a real search position. They are routed to a data check.

3. Methodology

Unit and outcomes. One row is one page of one client. Two outcomes are measured in June:

  • y_decline: June impressions are below 80% of May impressions. Base rate 0.704 over 90,966 pages. Seven in ten pages decline by this definition, so there is little room for any ranking to show lift.
  • y_low_ctr: June CTR is below the expected CTR of the page’s tier, defined only for pages with at least 100 June impressions. Base rate 0.570 over 65,088 labelled pages.

Baseline. A rule a person can read, with no fitted weights, written first and then frozen so the later comparison could not drift:

slip = how far May impressions fell below the page's own Mar-Apr monthly average (0 to 1) ctr_gap = how far the page's CTR is below its tier's expected CTR (0 to 1) visibility = percentile rank of the page's Mar-May impressions (0 to 1) score = visibility x (0.5 x slip + 0.5 x ctr_gap)

Each page also gets one reason code: slipping_visibility if slip is at least the CTR gap, otherwise ctr_below_tier_expected. A second reference ranks pages by visibility alone.

Features. Fifteen, all from March to May: log impressions (March–April, May, total), days with impressions, log average position and tier indicators, log CTR, tier-expected CTR, CTR gap, May-to-early ratio (capped at 5) and slip.

Models. Logistic regression (a readable linear model), a depth-3 decision tree (readable if/else), and a random forest (300 trees, depth 10, at least 50 pages per leaf, balanced class weights). Seed 42 throughout. The forest has to earn its place by beating both the rule and the simpler models on the same rows.

Validation. Five-fold GroupKFold by client, so no client appears in both training and test in the same fold. The fold test sets hold 1, 7, 10, 8 and 11 clients; fold 1 is one single client with 22,115 pages. The rule and the visibility ranking need no training but are scored on the same test rows, fold by fold. I report every fold and not only the average. The primary metric is P@K at K = 20, 50 and 100, next to the base rate, with AUC (how well the whole ranking separates the two groups) as a secondary view.

Leakage checks.

  • A timeline assertion: no June, outcome, score or identifier column is in the feature set.
  • An injected-leak test: adding a June-derived column should push scores toward 1.0. It did, to 1.000 on both outcomes, so the test harness can detect a leak.
  • A random-row split run beside the grouped split, to measure how much skill is client memorization.
  • Ablations that remove the CTR and momentum features.
  • One known mild issue: the tier-expected CTR is computed from March–May of all eligible pages, including pages that later sit in a test fold. It uses no June data, but it is not strictly training-only.

4.2 Is the edge stable, or only an average?

  • CTR outcome: stable. The forest wins five of five folds at P@50 (mean +0.216, interval +0.120 to +0.312, excludes zero), and beats the rule’s AUC in 16 of 17 clients inside their own data (median +0.121).
  • Decline outcome: directional. The forest wins three of five folds (mean +0.088, interval −0.008 to +0.220, includes zero). Fold 4 carries the average: without it the mean difference is about +0.015. Inside single clients it is ahead in 15 of 19, but its absolute AUCs sit between 0.50 and 0.64.

4.5 Where it is wrong

  • The most confident wrong calls on the decline outcome are pages that did fall in June, but by 3% to 11%, short of the 20% cut. They are near misses of a threshold, not unrelated picks.
  • In an earlier version, the most confident wrong CTR calls were tiny pages with a few hundred impressions and no clicks whose CTR recovered in June. That is what motivated a floor of 5 expected clicks before a page can enter the review queue.
  • Scores are for ranking, not for reading as probabilities: balanced class weights shift them about 0.15 to 0.20 below the actual decline rate in every tier.
  • Client concentration is real. In four of the five folds, 84% to 100% of the forest’s top 50 for decline comes from one client, so those folds mostly measure one client.

5. Limitations and honest framing

  • One month, one portfolio. Features cover three months and outcomes one. Seasonality, a different month or a different set of clients is untested, and no interval is reported on any single-month rate.
  • The CTR outcome rewards persistence. The features include March–May CTR and the outcome is June CTR. This is legitimate, with no June information in the features, but it is not independent evidence of hidden signal. In the top 20 of the review queue, all 19 labelled pages kept a low CTR in June.
  • The decline outcome is a weak target. Seven in ten pages meet it, so even a good ranking has little room to show lift, and the model’s edge there is directional.
  • Concentration. The review queue draws from 9 of 37 clients and contains no content-refresh items, because the CTR estimate covers three months of impressions and the slip estimate only one. I did not test a per-month normalization.
  • Thresholds are policy choices. The volume floors (100 and 50 impressions), the 20% decline cut, the top-20% model cut-off, the 5-expected-click floor, the 30% client cap and the 0.5/0.5 weights were not tested against alternatives.
  • A snippet or AI answer may take the click. For 19 of the top 20 pages the data cannot say whether a metadata edit could help.
  • No causal design. Nothing here shows that a refresh or a new title improves a page. The data is observational.
  • No claim about Google. This models outcomes in one portfolio; it says nothing about how Google ranks pages.

6. Ranked recommendations (action playbook)

Intended use. Each cycle, give a reviewer up to 50 pages from the review queue, no more than 30% from one client. Every page gets one action from an ordered rule; the first check that fires wins, and suspicious data is caught before any “edit the page” action.

Cost and value. Reading 50 pages takes about 10 hours. Using the measured June rates, the review queue is expected to contain about 48 pages with a real CTR gap, against 38 for the frozen rule and 28.5 for random picks (the estimate assumes unlabelled pages behave like labelled ones).

What must not be automated

  • Any edit to a page. The queue only orders candidates; a person accepts or rejects each one.
  • Pages routed to a data or technical check never reach a content edit before the check is done.
  • No sentence of the form “doing X will raise Y” in any report built from this queue.
  • Raw queries, URLs, titles and client names are never shown.

Before acting on a page, a person asks

  • Does the reason fit what I see on the live page and in the search result?
  • Is a sibling page absorbing the demand, or is there a seasonal or campaign explanation?
  • For a CTR item: does a snippet, answer box or AI answer take the click?
  • Is this client already over-represented in this cycle’s queue?
  • Were tracking and indexing problems ruled out?

Keeping it honest over time (proposed, not running)

Before each cycle, check that the data still looks like the data the model was built on (for example a drift score on position and CTR features). After each month’s real outcomes arrive, recompute P@50 for the model and for the frozen rule. If the model falls below the rule in two consecutive labelled periods, fall back to the rule-only queue until it is retrained, because added complexity has to keep earning its place.

7. Reproducibility

Everything lives in the repository. The notebooks run in order and each one reads the previous one’s output:

  1. w03_data_contract: the data contract, grain check and the deliberate-leak demonstration (March slice).
  2. w04_baseline_score: the warehouse query (cached locally), eligibility, the frozen rule, June outcomes, top-20 review.
  3. w05_model: three models, five client-grouped folds, comparison table, errors.
  4. w06_validation_audit: random against grouped split, per-fold and per-client stability, ablations, injected leak, claim rewrite.
  5. w07_action_playbook: out-of-fold scores for every page, the playbook rule, grading, exports and figures.
  6. capstone: consolidates the saved results this page is built from.
Seed
42 for every model and bootstrap.
Environment
Python 3.10.11, pandas 2.3.3, numpy 2.2.6, scikit-learn 1.7.2, matplotlib 3.10.9. Random-forest results can move a few points between library versions; the stable claims are the ranking of methods and the base-rate comparison, not the third decimal.
Data access
The release is gated on Hugging Face (free, instant approval). A read token is entered through a password prompt and never written into a notebook. The heavy warehouse scan runs once and is cached under work/outputs/.
What is not in the repository
Datasets and pseudonymous row-level queues are kept out of git on purpose. Metrics files and ID-free figures are committed. The numbers in this paper come from work/outputs/w07_metrics.json and the fold-level result files the notebooks write.
