## 2. Intended use and limits

**Who uses it, for what.** A content or SEO analyst with a limited review budget (this project assumes about 50 pages per cycle). The playbook gives them an **ordered list of pages worth looking at first**, one action and one reason per page, and a second short list of pages to **check for data or technical problems before anyone edits content**. It is **decision-support**: a person reviews every item before any change.

**What was measured (W4-W6, one month of outcomes, 37 clients, 90,966 pages, client-grouped 5-fold CV):**
- `y_low_ctr` (June CTR stays below the tier's expectation): base rate 0.566. Forest Precision@50 0.972 vs 0.756 for the frozen rule; ahead in 5/5 folds (90% bootstrap interval of the difference +0.120 to +0.312) and in 16/17 clients on within-client AUC.
- `y_decline` (June impressions below 80% of May): base rate 0.701. Forest Precision@50 0.852 vs 0.764 for the rule, but ahead in only 3/5 folds, interval -0.008 to +0.220 (includes zero), and one fold carries the average. This is **directional only**.
- Random-row split inflated the forest on `y_decline` (P@50 1.000 vs 0.852 grouped), so all numbers here use the grouped split.

**Known limits (carried from W4-W6, re-stated here so the playbook cannot be read without them):**
- **Persistence.** Part of the `y_low_ctr` skill is a page keeping a CTR gap it already had. Without the CTR features the ranking quality over the whole list drops (AUC 0.760 to 0.624); the top of the list stays easy (P@50 0.944).
- **Weak decline model.** For `y_decline` the momentum signal (`slip`) adds little beyond exposure and position (W6 ablation), and absolute AUC is about 0.60. So `review_content_refresh` is labelled **directional** in every output.
- **Client concentration.** In W6, four of five folds had a top 50 that was 84-100% one client. Here the review queue is capped at 30% per client: uncapped it has 7 clients with the largest at 50%, capped it has 9 clients with the largest at 30%.
- **One month, one portfolio.** No seasonality, no later month, no uncertainty on single-month P@K.
- **Not causal.** The queue says which pages look worth reviewing first. It does **not** claim that a refresh or a metadata edit will cause recovery.
- **Model scores are for ranking, not probabilities.** The forest uses balanced class weights, so predicted values sit below real rates (seen in W5).

## 4. Monitoring / retrain triggers

**Two clocks.** The playbook can go stale in two different ways, and they are noticed at different times.

**Pre-release (before a queue reaches a reviewer): data looks the same as when the model was built.**
- Row count and columns match expectations (`need` set in Section 0).
- `pre_release_checks()` returns `ok` (client share, missing scores, impossible positions).
- No feature has drifted far from the population the model was trained on. Below, a PSI check (population stability index: how much a distribution moved; rule of thumb, not a law: under 0.1 small, 0.1-0.25 moderate, over 0.25 large). In this one-month release there is no "next month" to compare against, so the demonstration compares the **largest client against all other clients**: the same kind of shift a new client would bring, which is exactly what W6 showed matters.

**Post-label (after the next month's real outcomes are known).**
- Recompute Precision@50 for the model and for the frozen baseline on the new month, and the new base rate.
- If the base rate shifts materially, treat the next queue as provisional.
- **Retrain / fall-back trigger (proposed policy, not yet running):** if the model's Precision@50 is below the baseline's for **two consecutive labelled periods**, fall back to the rule-only queue until the model is retrained. Complexity has to keep earning its place.

def psi(ref, new, bins=10):
    ref, new = pd.Series(ref).dropna(), pd.Series(new).dropna()
    edges = np.unique(np.quantile(ref, np.linspace(0, 1, bins + 1)))
    if len(edges) < 3:
        return np.nan
    edges[0], edges[-1] = -np.inf, np.inf
    r = np.histogram(ref, edges)[0] / len(ref)
    n = np.histogram(new, edges)[0] / len(new)
    r, n = np.clip(r, 1e-4, None), np.clip(n, 1e-4, None)
    return float(np.sum((n - r) * np.log(n / r)))

def fallback_trigger(model_vals, base_vals, periods=2):
    below = [m < b for m, b in zip(model_vals, base_vals)]
    run = best = 0
    for x in below:
        run = run + 1 if x else 0
        best = max(best, run)
    return best >= periods, below
